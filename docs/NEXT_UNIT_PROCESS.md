# Review of the RSP-550 project and the process for the next unit

Written 2026-11-03 after SSP-550 1.6.8, at the user's request: look at every step so far and find the faster way for the
next device. The RSP-550 took ten hardware runs, eight releases (1.5.4 to 1.6.8) and three listening rounds over about
three weeks. Most of that time went to discovering things one run at a time that one well-designed run would have
captured at once, and to hand analysis that should have been a pipeline. The next unit should need two unattended
captures, one automatic fit, and one short listening round.

## What actually happened, step by step

| Step | How it went | What it cost |
|---|---|---|
| Intake (manuals, SysEx, ROM) | Good. The parameter map and program format came from documents and were right. | One chat. |
| Plug-in written first, from documents | The engine's structure was guessed (e.g. modulated reverbs, 0.707-Q shelves at 160 Hz / 6 kHz) and later bent to measurements with scale factors. Some guesses (reverb modulation, EQ corners) survived until run 10. | Every wrong guess cost a run to find and a release to fix. |
| Run 1: every stored program, one stimulus | Found the big level and decay errors. Right first step. | One session. |
| Runs 4-8: one hypothesis per run, designed from the previous run's findings | Each run answered its question and raised the next one. Phaser, flanger, chorus, vocoder, pitch, rotary each needed its own round; follow-up rounds (run 7) needed the user present. | Five sessions with the user at the keyboard, one chat each. |
| Run 9: the reference-lab battery | 38 of 86 captures lost to a loose left return, found only in analysis. | A session and a retake run. |
| Runs 10/10b | Interface stalled on the 96 kHz switch; the left return sagged again on five captures; loop gain mis-read by 4.8 dB from a cross-session comparison; sweep deconvolution read the top octave low (the unit's own clock); the pre-delay test was dominated by the direct sound. | Two sessions; three of five findings were about the measurement, not the unit. |
| Fits (1.5.4 to 1.6.8) | Each fit was scratchpad scripts and hand-tuned constants written into C++ comments ("run 7: x0.84"). Reproducible only by reading the chat. The engine-only renderer (render4) drifted from the plug-in and misled a fit. | Every fit a chat's worth of context; 105 constants with no re-derivation. |
| Gating tests | Arrived late (run 9) and immediately found real bugs: no host reset, Auto Gain depending on buffer size, NaN sticking, DC passing, rate-dependent filter coefficients. Since then they have caught every regression before release. | Cheap once written; expensive for having been written late. |
| Listening | Seven results across three builds, 10 trials each. They were the only signal on what is audible, and they also had to stand in for pipeline verification. | The user's time, the scarcest resource. |

## The faults, by root cause

1. **Measurement before model, not after.** The model's structure was chosen before anything was measured, so measurements became corrections to a guess. Measure first, then choose the structure from the measurements (a reverb with no modulation, shelves with the measured Q).
2. **Serial runs.** Ten runs because each tested one idea. A battery designed from the parameter map (every control at several values, every algorithm, wet-only and direct-only, three stimulus types) captures in one unattended session what runs 4-10 found over weeks.
3. **Loop health found in analysis, not in the run.** Three runs lost data to one jack. The runner now retakes dead returns; it must also check per-channel balance every quarter second against the stimulus, keep a reference program every N captures (not only at the end), and run the loop check first, every time.
4. **Calibration by inference.** Loop latency and gain were derived from the unit's own signals and from cross-session comparisons; one of those was wrong by 4.8 dB and made the stereo look broken. A permanently patched interface output-to-input pair gives exact latency and gain every run without touching the unit.
5. **Stimuli that assume a shared clock.** Sweep deconvolution on a free-running digital unit is biased at the top. The battery should measure the unit's clock from a long tone and resample before deconvolving, or use stimuli that do not need it (steady noise, impulses, tones).
6. **Hand fits.** Constants in comments cannot be re-derived or audited. Fitted values belong in a per-device table generated by scripts from the captures and consumed by the build; a fit then re-runs with one command and a changed capture changes the table, not a chat.
7. **Two renderers.** The analysis renderer and the plug-in diverged (1.6.4) and a fit was made against the wrong one. One renderer: the plug-in itself, headless.
8. **Tests written after the bugs.** The dci-core checks and the rate check found bugs that had shipped for several releases. For the next unit they run from the first build.
9. **Chats as the record.** Each fit lived in a chat's context and scratchpad; disk filled, context compacted, and the next chat could not reproduce the last. Everything in the repo from the first day; the chat is where decisions are made, not where work is stored.

## The process for the next unit

Target: the user does three things per capture (patch the unit in, double-click, restore the unit's memory at the end), and one short listening round per release. Everything else is scripted and runs the same for every device.

### 0. Fixed bench
- Interface outputs A/B to the unit, unit outputs to interface inputs C/D, and one interface output patched straight to one input for calibration. Never moved. The runner reads the calibration loop at the start of every run: exact latency, exact gain, interface noise floor.
- Loop check with per-channel balance and sag detection runs first, every run, and the run refuses to start on a fault.

### 1. Intake (one chat, documents only)
- Parameter map, program format, SysEx write/read, which slots are safe to write, how restore works (and whether it needs the front panel: the RSP-550 does, so the user restores; a unit that accepts a bulk load unattended needs no user at the end).
- A device profile in `devices/<unit>/`: parameter table with type (level, time, frequency, depth, rate, switch, enum), range, step and unit, from the manual. This table drives everything below.

### 2. One battery, generated from the profile
- **Every stored program** with the standard stimulus (impulse x4, pink noise, long tones, clicks, music): the baseline and the repeatability reference.
- **Every control, three to five values**, on one or two carrier programs per algorithm, wet-only: the control laws (level in dB per code, time per code, frequency per code, depth, rate). A generic extractor fits each law from its type; this replaces most of the RSP-550's 105 hand-fitted constants.
- **Every algorithm wet-only and direct-only** at factory settings: routing, stereo, linearity (input doubled: output doubled or not), time variance (click trains: modulated or not). These classify each algorithm and choose which measures and which engine structure apply.
- Reference program every 20 captures; the whole battery twice if time allows (repeatability within and across sessions).
- No rate switching inside a run; a second run at 96 kHz if the device supports it.
- Size: a few hundred to a thousand captures, 10-20 s each, run unattended overnight with automatic retakes.

### 3. Pipeline, one command
`devices/<unit>/pipeline.sh` runs: guards on every capture (clip, dropout, balance, dead return, clock drift) -> calibration applied -> measures per capture -> repeatability (tolerance per measure from the unit's own spread) -> control laws -> fit table (`fit.json`) -> plug-in build from the table -> gating tests (plug-in checks, host reset, rate, parity, self-test) -> run-battery comparison on ours -> audibility score per program -> listening page published with the programs the score flags. Each step writes its own report; the last line is the verdict.

### 4. Model from the measurements
- Linear blocks (EQ, filters, crossovers) are identified directly: fit biquad coefficients to the measured transfer function, not a guessed topology at a guessed corner.
- Time structure (reflections, onset, build-up, decay shape) fitted by the optimiser on the engine's shape controls, as done by hand for 1.6.8, but from the pipeline.
- Modulation only where the time-variance test found it, at the measured rate and depth.
- Every engine control neutral by default and null-tested against the previous release.

### 5. Listening only where it counts
- The audibility score (calibrated on the seven RSP-550 results) ranks all programs; the user listens to the top few and to any the score calls borderline. Six programs x ten trials per build becomes two or three.
- The page stays the same: one URL, results kept, "can't tell" allowed.

### 6. Chat discipline
- One chat per phase (intake, first battery, fit review, release). Hand-off in STATUS. Nothing of value in a scratchpad: scripts and results go into the repo the moment they work.
- The heavy computation (renders, replay, fits) runs on the Mac runner through the mac-tests workflow, not on the two-core workspace.

## Ideas worth trying on the next unit

- **Clock-drift correction**: measure the unit's sample clock from a 10 s tone (frequency to 0.01 Hz) and resample every capture to it before any deconvolution. Removes the sweep bias and makes sweeps usable again for decay.
- **Generic control-law extractor**: for each parameter type a fixed model (dB-linear, ms-linear, log-frequency, percent) fitted to 3-5 points with residual reported; a parameter whose residual is large gets a finer sweep in the second run automatically.
- **Linearity and time-variance classifiers per algorithm** decide the measures and the engine structure before anyone writes DSP.
- **Direct biquad identification** for every static filter in the device (program EQ, feedback filters, crossovers): the coefficients are the fit, no corner-frequency guessing.
- **Same-chain comparison**: render the plug-in on the Mac (PluginRender) and play it through the same interface loop as the unit, so converter colouring and the loop are in both captures and cancel.
- **Two-run plan by default**: run A is the generic battery; the pipeline's gap report (large residuals, untested controls, measures outside the unit's spread) writes run B. No run C without a reason.
- **Audibility score** as the gate on the user's time, and as a regression test: a build may not raise any program's score above its previous value.

## What this would have saved on the RSP-550

Runs 4-8 (five attended sessions) collapse into run A; runs 9-10b's three measurement mishaps are caught by the fixed bench and the guards before data is lost; the 1.6.7 and 1.6.8 fits (two chats of hand analysis) run from the pipeline in an hour; and the user's listening drops from eighteen tests to about six. The intake, the first battery and one fit review remain. Estimate for a unit of similar complexity: two unattended captures, three chats, one listening round.
